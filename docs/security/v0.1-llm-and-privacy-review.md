# MeetingOS v0.1 — LLM Security & Data Privacy Review

**Date:** 2026-09-07
**Scope:** `backend/meetings/`, `backend/ai/`, `backend/routes/meetings.py`, and the
ingestion → cloud-API data path. Frontend reviewed only for output-handling sinks.
**Frameworks:** OWASP Top 10 for LLM Applications (2025); NIST AI RMF 1.0; GDPR.
**Method:** static review of source, configuration, and tests. No code executed against
a live provider — see *Evidence limits*.

---

## Executive summary

The model-facing code is the strongest part of this system. Prompt injection is
defended structurally rather than by instruction, and the copilot's citation path —
the specific concern raised for this review — turns out to carry no injectable sink at
all, because a citation is a typed integer and a `<button>`, not a URL.

The risk is concentrated elsewhere: **everything MeetingOS knows about a meeting is
sent to a third-party inference API**, over an endpoint that was, until this review,
read from an unvalidated environment variable. Six findings were rated High or above.
Five are fixed. One — no authentication on any endpoint — is not fixable in this phase
and remains the blocker on deploying v0.1 anywhere but a private machine.

| Severity | Found | Fixed | Open |
|---|---|---|---|
| Critical | 1 | 0 | 1 |
| High | 5 | 5 | 0 |
| Medium | 4 | 3 | 1 |
| Low / Informational | 3 | 0 | 3 |

## Part 1 — OWASP LLM Top 10 (2025)

### LLM01 — Prompt injection via transcript content · **Low**

The three modules that put transcript text in front of a model —
`intelligence.py`, `copilot.py`, `curation.py` — share one pattern, and it is the right
one:

- System prompts are module constants with no interpolation. Transcript text cannot
  reach the instruction channel, and there is a test per module asserting the system
  prompt is byte-identical to the constant after processing an injection payload.
- Excerpts are fenced (`BEGIN TRANSCRIPT EXCERPT (untrusted data)`) and newlines inside
  a segment are flattened, so a segment cannot forge its own fenced line
  (`test_transcript_newlines_cannot_forge_an_excerpt_line`).
- Output shape is fixed before the call: schemas come from a hardcoded table, every
  enum is a `Literal`, and no model output indexes into a dispatch table.
- Citations are whitelisted against the segments retrieved for *this* meeting, so a
  fabricated id is dropped before it reaches a query
  (`test_citation_cannot_reach_another_meetings_segment`).

Eval case `10-injection-in-transcript` carries a spoken injection payload with a
`must_not_contain` assertion, so the eval fails if payload text ever reaches an
extracted item.

Rated Low rather than Informational because the defenses are structural but the
*consequence* of a bypass is unbounded: extracted items land in a governance record
that people act on. Residual risk is a model that is simply persuaded — no code change
prevents that, which is what the verifier exists for.

### LLM02 — Sensitive information disclosure via cloud API calls · **High → fixed (partly)**

**Finding 1 — Unvalidated inference endpoint.** `OPENAI_BASE_URL` was read raw in
`openai_provider.py:44` and `whisper_cloud_provider.py:45`, and used as the destination
for both meeting audio and full transcripts. Anyone able to set one environment
variable could redirect every recording to a host of their choosing, with nothing in
the logs marking the change. The shipped `.env` points at OpenRouter — an aggregator
that forwards to third-party inference hosts — on a free-tier model.

*Fixed:* `config.validate_inference_base_url()` enforces a host allowlist, refuses
plaintext HTTP to a remote host, and logs the resolved endpoint at startup. Extending
the allowlist requires setting `MEETINGOS_ALLOWED_INFERENCE_HOSTS` explicitly, which
makes a data-residency change a deliberate, visible act. Five tests.

**Finding 2 — No redaction before egress.** Full transcript text left the machine with
no filtering. *Fixed:* `backend/meetings/redaction.py`, wired into all three egress
paths. Opt-in via `MEETINGOS_REDACT_TRANSCRIPTS=1`. See Part 2 for what it does and
does not cover.

**Finding 3 — Cross-tenant read.** Retrieval applies no authorization filter, so any
caller reads any organisation's transcripts. **Not fixed** — this is the auth finding
below, not a retrieval bug.

*Not found:* no secrets in system prompts; no prompt/completion logging (`grep` for
logging of prompt or completion text returns nothing in `backend/ai/` and
`backend/meetings/`).

### LLM05 — Improper output handling in the copilot's citation links · **Low**

This was flagged for specific review, and the answer is that the concern does not
apply in the shape it usually takes. There is no citation *link*:

- `CitationTime` takes `ms: number` — a typed integer, not a URL — and renders a
  `<button>` that calls `seek(ms)` on a local store. No `href`, no `window.open`, no
  path construction.
- The citation's displayed text (`citation.text`, `speaker_label`) is read from the
  database **after** the segment id passes the whitelist. It is transcript content, not
  model output.
- `response.answer` is model output, rendered as a React text child and therefore
  escaped. There is no markdown renderer anywhere in `web/src`.
- A repo-wide grep for `dangerouslySetInnerHTML`, `innerHTML`, `eval(`, and
  `new Function` returns two hits, both static `href` values in navigation.

Residual: model output is displayed to a human who may act on it. That is LLM09, and it
is handled — see below.

### LLM06 — Excessive agency · **Informational**

The copilot registers no tools; the MCP server registers none either. There is no code
path from a model output to an action. `test_copilot_module_exposes_no_action_taking_tools`
greps the module for `smtplib`, `subprocess`, `requests.post`, `db.add(`, `db.delete(`
and fails if any appears — so this is asserted, not assumed. The confirmation gate for
future action tools is deliberately *not* built yet.

### LLM08 — Vector and embedding weaknesses · **Medium → open**

Segment embeddings are stored unencrypted in SQLite alongside their source text, with
no access control (no auth exists). Text embeddings are partially invertible, so they
are personal data, not an anonymous index. `MIN_SIMILARITY = 0.25` does gate retrieval,
which addresses the adversarial-retrieval half of this category.

Mitigated in part by the retention purge (below), which now deletes embeddings with
their transcripts rather than leaving them behind. Fully closing this requires
encryption at rest and the auth work.

### LLM09 — Misinformation · **Informational — handled well**

Worth recording as a strength. Every extracted item carries a verification status and
score; the verifier's two-signal design (verbatim-quote gate OR embedding similarity)
catches invented claims; low-confidence and unsupported items are surfaced in the UI
with distinct colour *and* icon *and* wording rather than hidden. The copilot returns
`NOT_DISCUSSED` as a first-class answer and never invents one when retrieval comes back
empty — it does not even call the model in that case. Temperature defaults to 0.2.

### LLM10 — Unbounded consumption · **High → fixed**

`POST /ask` costs an embedding call plus a generation call per request, and `POST
/upload` buys a transcription plus four extraction calls per topic. Neither was
authenticated or rate limited: a trivially scriptable denial-of-wallet.

*Fixed:* `backend/routes/limits.py` — a fixed-window per-client limiter, 20 asks and 5
uploads per minute by default, returning 429 with `Retry-After`. Combined with the
upload size cap and processing concurrency bound added in the previous phase. Three
tests. **Limitation, stated in the module:** the counter is in-process and keyed on
client IP, so it bounds accidental and casual abuse, not a determined attacker behind
rotating addresses. The real fix is auth plus per-account quota.

### LLM03 / LLM04 / LLM07 — Not applicable or clean

No models are downloaded or deserialized (LLM03 — no `pickle.load`, no `torch.load`).
No fine-tuning and no user-writable knowledge base (LLM04). System prompts contain
behavioural instructions only — no credentials, no internal URLs, no business rules
whose disclosure would matter (LLM07).

## Part 2 — AI data privacy: the ingestion → cloud path

### What leaves the machine

| Stage | Payload sent | Destination |
|---|---|---|
| Transcription | **The entire audio file**, raw bytes | `OPENAI_BASE_URL` (`/audio/transcriptions`) |
| Segmentation | Every segment's text, batched | Embeddings endpoint |
| Extraction | Full transcript text, per topic, ×4 schemas | Chat completions |
| Topic titling | Up to 2000 chars of transcript per topic | Chat completions |
| Verification | Every claim + every cited segment's text | Embeddings endpoint |
| Copilot (backfill) | Every segment's text, once per meeting | Embeddings endpoint |
| Copilot (per question) | Up to 12 retrieved segments + the question | Chat completions |

**In effect the entire meeting leaves the machine, twice** — once as audio, once as
text — plus once more per question asked. Speaker labels travel with the text.
`Speaker.voice_embedding` (biometric) does not egress; it is stored locally.

Default destination is OpenRouter, an aggregator that routes to third-party inference
hosts. On a free tier, provider terms commonly permit training on submitted data. No
DPA has been reviewed; no zero-data-retention option is configured.

### Findings

**P1 — Is a redaction pass needed before testing beyond your own club meetings?**
**Yes.** This was the question asked, and the answer is unambiguous. For a student club
discussing showcase dates the exposure is defensible with informed self-consent. The
moment a participant reads out a phone number, an address, a bank reference, or a
health detail, that identifier is disclosed to a vendor and its downstream hosts.

*Fixed:* `backend/meetings/redaction.py` covers emails, phone numbers, card numbers,
IBANs, sort codes, NI and SSN numbers, postcodes, and URLs, replacing each with a typed
placeholder (`[redacted:phone]`) so the surrounding statement stays extractable. Wired
into all three egress paths, opt-in via `MEETINGOS_REDACT_TRANSCRIPTS=1`, off by
default because it measurably degrades extraction detail and that should be a choice.
Twelve tests, including one asserting ordinary meeting speech is left untouched.

**It deliberately does not redact names,** and this is the honest limit: "Priya will
chase the invoice" *is* the action item, and a transcript with names stripped extracts
to nothing. That makes this mitigation, not anonymisation. A meeting that genuinely
must not leave the machine needs a local model, not this flag.

**P2 — Retention was declared but never enforced · High → fixed.**
`Organization.retention_days` has defaulted to 365 since the first schema and nothing
ever read it. `DELETE /api/meetings/{id}` returns 501. Nothing had ever been deleted.
A retention period no code enforces is worse than none — it reads as a control in
exactly this kind of review while deleting nothing.

*Fixed:* `backend/meetings/retention.py` + `just purge`. Deletes expired meetings,
their transcripts **and embeddings**, speakers **and voice embeddings**, extracted
items, and the recording file. Dry run by default. Four tests.

**P3 — No consent mechanism · Medium → open.** No record that a participant was told
their recording is sent to a third-party model, and no opt-out. Not fixable in code
alone: it needs a product decision about consent capture at upload. Documented here so
it is not discovered later. Under GDPR Art. 6 this needs a legal basis before any
recording involving people other than the author.

**P4 — `is_redacted` column is decorative · Low → open.** `TranscriptSegment.is_redacted`
exists and is never read or written anywhere. Either wire it to the redaction pass or
drop it; a flag that lies is worse than no flag.

**P5 — No audit trail · Medium → open.** No record of who accessed a transcript or what
a given LLM call cost. `Usage` is returned by every provider and persisted nowhere, so
per-meeting cost is unmeasurable and an anomalous spend spike undetectable.

## Open: the one that blocks v0.1

**No authentication or authorization on any endpoint · Critical.**

The schema is multi-tenant throughout — `Organization`, `User.role` with `board` and
`auditor`, `Meeting.visibility`, `org_id` on every table — and none of it is enforced.
`_resolve_org()` documents this itself: *"This whole function goes away when auth
lands."* The Dockerfile binds `0.0.0.0`.

Anyone who can reach the port reads every organisation's meeting audio, transcripts,
decisions, risks, and `Speaker.voice_embedding`. This also makes the rate limiter
IP-keyed rather than account-keyed, and makes LLM02's cross-tenant read unfixable.

**Do not deploy v0.1 outside a private machine or network until this lands.** It is the
next piece of work, ahead of any new feature surface.

## Evidence limits

Static review only. Nothing here was tested against a live model, because no provider
credentials exist on this machine — so claims about *defenses* are grounded in code and
tests, while claims about *model behaviour under adversarial input* are not empirically
verified. The eval suite's injection case will exercise that on the first credentialed
run.

The eval cases are hand-authored, not cut from real recordings
(`backend/tests/eval_cases/README.md`). No real meeting has ever been recorded or
processed by this system.
